Especificações Técnicas & Metodologia Superpowers

Documentação completa dos artefatos de engenharia de software gerados pelo processo agentic: especificações de design, planos de implementação e matriz de execução com garantia de qualidade.

Superpowers é um framework de engenharia agentic disciplinada desenvolvido para conduzir sistemas de Inteligência Artificial autônomos com o mesmo (ou superior) rigor metodológico aplicado pelos melhores times de engenharia de software mundiais.

1. Brainstorming

Exploração crítica de requisitos, formulação de premissas técnicas, identificação de riscos de negócio e validação prévia com os stakeholders antes de escrever qualquer linha de código.

2. System Design Spec

Criação de documento de arquitetura imutável e detalhado: entidades, matriz de erros, modelos transacionais, algoritmos de cálculo financeiro e limites arquiteturais.

3. Implementation Plan

Decomposição estrita em tarefas atômicas sequenciais ou paralelizáveis, contendo arquivos envolvidos, interfaces expostas, passos executáveis e critérios de verificação.

4. Subagent-Driven Dev

Orquestração de subagentes especializados executando cada tarefa em contextos limpos, com briefs direcionados, sem poluição de contexto e com relatórios formais de encerramento.

5. TDD / BDD Obrigatório

Garantia absoluta de que testes automatizados (Cucumber BDD e JUnit 5) validam cada requisito antes do aceite. Nenhuma funcionalidade é considerada concluída sem evidência de testes passando.

6. Verification Before Completion

Regra de ouro do framework: "Evidência antes de asserções". Comandos reais de build e verificação (mvn verify) devem ser executados no ambiente real antes de emitir o parecer de conclusão.

Pilares de Rigor e Governança
Habilidade (Skill) Propósito & Quando Utilizar Impacto na Qualidade da Solução
brainstorming Antes de qualquer trabalho criativo, especificação ou codificação. Evita retrabalho, resolve ambiguidades em regras de negócio e define arquiteturas robustas antes do primeiro commit.
writing-plans Após validação do design spec para quebrar tarefas em passos atômicos. Elimina derivação de escopo e assegura rastreabilidade ponta a ponta dos requisitos.
subagent-driven-development Durante a execução técnica das tarefas do plano. Preserva o contexto do agente principal, permite revisões independentes de código e gera relatórios auditáveis.
test-driven-development Ao implementar qualquer funcionalidade ou correção. Garante que o comportamento esperado é verificado previamente por testes antes da escrita do código de produção.
verification-before-completion Antes de declarar qualquer tarefa ou plano como finalizado. Impede anúncios prematuros de sucesso; todo término exige evidência concreta de testes e compilação sem alertas.

System Design Specification da API BNPL

2026-09-18-bnpl-system-design.md

Especificação técnica de arquitetura de software contendo o modelo de dados, políticas de segurança, conciliação monetária e tratamento unificado de erros.

Fórmulas Financeiras & Amortização
Cálculo de Juros e Comissão
commissionAmount = round(amount * interestRate, 2, HALF_EVEN);
totalAmount = amount + commissionAmount;
Algoritmo de Divisão em 5 Parcelas Quinzenais
baseInstallment = floor(totalAmount / 5, 2);
finalInstallment = totalAmount - (baseInstallment * 4);

// Parcela 1 a 4: baseInstallment
// Parcela 5: finalInstallment (garante soma exata sem perda de centavos)
Precisão Monetária: Todas as variáveis financeiras utilizam BigDecimal com arredondamento bancário RoundingMode.HALF_EVEN e tipos SQL NUMERIC(15, 2).
Matriz Transacional e Concorrência
Consistência de Crédito

A operação de compra (POST /v1/loans) é executada com anotação @Transactional e nível de isolamento padrão do Spring Data JPA sobre o PostgreSQL.

  • Verificação atômica de amount <= availableCreditLineAmount.
  • Subtração simultânea do saldo disponível: availableCredit = availableCredit - amount.
  • Criação coordenada da entidade LoanEntity e dos 5 registros filhos InstallmentEntity vinculados por chave estrangeira em cascata.
Autenticação JWT Stateless

Ao registrar um novo cliente (POST /v1/customers), o sistema gera um token JWT com algoritmo HMAC-SHA256, contendo o UUID externo e claims de emissão, retornado no header X-Auth-Token. Esse token é exigido nos endpoints subsequentes via cabeçalho HTTP padrão Authorization: Bearer <token>.

Matriz Completa de Códigos de Erro da API
Código Aplazo Nome do Erro HTTP Status Descrição do Cenário de Disparo
APZ000001 INTERNAL_SERVER_ERROR 500 Falha inesperada no servidor ou indisponibilidade de banco de dados.
APZ000002 INVALID_CUSTOMER_REQUEST 400 Dados inválidos de cadastro ou idade fora da faixa permitida (menor de 18 ou maior de 65 anos).
APZ000004 INVALID_REQUEST 400 Formato de identificador inválido (não é UUID) ou payload JSON com sintaxe corrompida.
APZ000005 CUSTOMER_NOT_FOUND 404 Cliente inexistente ao consultar por ID ou tentar criar empréstimo.
APZ000006 INVALID_LOAN_REQUEST 400 Valor de empréstimo superior ao limite de crédito disponível ou valor menor/igual a zero.
APZ000007 UNAUTHORIZED 401 Token JWT ausente, expirado ou com assinatura HMAC inválida.
APZ000008 LOAN_NOT_FOUND 404 Empréstimo inexistente para o identificador UUID pesquisado.
